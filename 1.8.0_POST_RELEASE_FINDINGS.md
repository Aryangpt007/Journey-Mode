# 1.8.0 Post-Release Findings — Sound/Toast Bug & Deposit-Screen Hang

> **Status: all findings below are resolved in 1.8.1** (staged in `release_1.8.1/`, all 9 environments rebuilt from current `HEAD`). The diagnosis is kept verbatim as the record of what was wrong and why; see [Resolution — 1.8.1](#resolution--181) at the foot of the file for what each fix actually was, plus the additional issues the follow-up audit turned up.

Investigation notes from a single session auditing user reports against the shipped 1.8.0 build. Two independent bugs were found and root-caused; neither had been fixed in code at the time of writing (diagnosis only, per instruction). Filed alongside [JM_Project.md](JM_Project.md) (architecture) and [JOURNEY_MODE_CHECKLIST.md](JOURNEY_MODE_CHECKLIST.md) (feature tracker) as a record of what was found and why, so the fix work didn't have to re-derive any of this.

## 1. Achievement sound / on-screen toast still firing (stale shipped artifact, not a source bug)

**Symptom reported:** the `UI_TOAST_CHALLENGE_COMPLETE` sound plays on every Journey Mode unlock, plus an on-screen notification — both of which JM_Project.md §12 claims were finalized to "message-only, no sound" before 1.8.0 shipped.

**Root cause: the committed source is clean; the *shipped jars* are not.**

- Grepped all 9 environments (case-insensitive, every file type) for `playSound`, `SoundEvents.*`, `UI_TOAST_CHALLENGE_COMPLETE` (including as a raw lowercase resource-location string), `Advancement`, reflection, and Mixin configs. Zero executable hits anywhere in the git-tracked source at `HEAD` (`0c12da4`, same commit as `main`). The only matches were stale prose in comments.
- The installed jar (`journeymode-Forge_1.8.0_1.20.1.jar`, tested by the reporting user) is **byte-for-byte SHA256-identical** to `release_1.8.0/journeymode-Forge_1.8.0_1.20.1.jar` — the staged copy sitting in this repo, built **2026-07-26 14:12**, roughly 16 minutes after the single squashed 1.8.0 commit (`35c8e18`, authored 13:56). That staged build predates whatever later, never-committed-separately edit actually stripped the sound call from the `.java` source. The jar was never rebuilt after that fix.
- Confirmed via bytecode inspection + local ForgeGradle SRG mapping cache (`srg_to_official_1.20.1.tsrg`): the shipped `ClientSetup.class` for Forge 1.20.1 contains a real call `playSound(SoundEvents.UI_TOAST_CHALLENGE_COMPLETE, F, F)` (`f_12496_` → `UI_TOAST_CHALLENGE_COMPLETE`, `m_5496_` → `Entity.playSound(SoundEvent,float,float)`). This is genuine compiled bytecode, not a false positive.

**Scope — checked all 9 staged jars in `release_1.8.0/` the same way:**

| Environment | Sound call present in staged/shipped jar? |
|---|---|
| Forge 1.12.2 | **Yes** (`SyncJourneyDataPacket$Handler.class`) |
| Forge 1.16.5 | **Yes** (`ClientSetup.class`) |
| Forge 1.19.2 | Clean |
| Forge 1.20.1 | **Yes** (`ClientSetup.class`) — the one the report came from |
| Fabric 1.16.5 / 1.19.2 / 1.20.1 / 1.21.1 | Clean, all four |
| NeoForge 1.21.1 | **Yes** (`ClientSetup.class`) |

Since JM_Project.md states 1.8.0 is "live on GitHub Releases, CurseForge, and Modrinth, across all 9 environments," and these staged jars are what get uploaded, **the actual public downloads for Forge 1.12.2, 1.16.5, 1.20.1, and NeoForge 1.21.1 almost certainly carry this bug right now**, independent of anything in this local repro.

**Fix required:** not a code change (source is already correct) — rebuild those 4 jars from current `HEAD` and re-stage/re-upload them, replacing the stale artifacts. `check-parity.ps1` (JM_Project.md §2/§14, "not yet built") would have caught this class of drift — a jar-vs-source verification gate is worth prioritizing precisely because of this incident.

**Secondary cleanup found along the way (cosmetic, no behavior impact):**
- Stale Javadoc/comments still read *"unlock sound + action-bar message"* in 7 of 9 environments (Fabric 1.16.5/1.19.2/1.20.1/1.21.1, Forge 1.12.2, Forge 1.16.5, NeoForge 1.21.1) — leftover text from before the sound was removed. Only Forge 1.20.1 and Forge 1.19.2 got the comment corrected to drop "sound."
- Unused `import net.minecraft.sounds.SoundEvents;` still sits in `Fabric_1_16_5/src/main/java/.../network/FabricNetworkHandler.java:17`, referenced nowhere.
- `JOURNEY_MODE_CHECKLIST.md:263` (§11 Visual Polish) still lists "Unlock sound + toast/particle on threshold crossing" as an **unchecked TODO** under `Status: TODO`, contradicting JM_Project.md's account that this was actually built and then explicitly reverted. The tracker was never updated to match reality.
- **Real parity gap, unrelated to the above:** `Forge_1_19_2/.../client/ClientSetup.java:68-75` (`handleSync`) calls the older 5-argument `updateFromSync(...)` overload and never calls `getAndClearNewlyUnlocked()` — so the action-bar celebration message never fires on that environment at all, and `teamDisplayName` never syncs there either. This contradicts JM_Project.md §2's claim that "every item... shipped identically to all 9, compile-verified."
- **Duplicate notification systems:** an *older*, separate code path (`JourneyModeMenu.java:185-189` and `:248-253`, `journeymode.unlock_message`) sends a real **chat** message directly from the deposit-handling logic on every single-slot unlock, independent of and in addition to the newer sync-diffed action-bar celebration (`celebrateNewUnlocks`). Both fire for the same event. Not a bug per se, but worth knowing before touching either.

## 2. Deposit-screen hang/freeze on placing certain items (genuine current-code bug)

**Symptom reported:** placing an item in the deposit slot with a specific mod list freezes the game — no crash report, no `latest.log` entry, no `hs_err_pid` file. Reproduced independently on a clean Forge 1.20.1 build with the reported mod list.

**Diagnosis path:** a `jstack` thread dump while frozen showed the Render thread pinned at ~100% CPU (48.6s of 75.7s elapsed) inside `RecipeDepthCalculator.getRecipeDepth` ↔ `calculateRecipeDepth` mutual recursion, called from `JourneyModeScreen.renderDepositTab:224` → `JourneyDataAttachment.getThreshold:157`. Two follow-up heap dumps (`jhat` + OQL queries against the live `calculating`/`cycleTainted` `Set<Item>` fields) and, finally, a one-off debug-logging build (temporary, never committed — see below) nailed the exact mechanism.

**Root cause — three factors compounding, not one bad mod:**

1. **[`JourneyModeScreen.java:224`](Forge_1_20_1/src/main/java/com/aryangpt007/journeymode/client/gui/JourneyModeScreen.java:224)** (`renderDepositTab`) calls `data.getThreshold(slotItem.getItem())` **unconditionally on every rendered frame** the Deposit tab is open, with zero caching at the GUI layer.
2. **[`RecipeDepthCalculator.java:157-161`](Forge_1_20_1/src/main/java/com/aryangpt007/journeymode/data/RecipeDepthCalculator.java:157)**: any item whose depth resolution touches a real cycle is deliberately **never memoized** — by design, per the 1.8.0 "cycle-cache nondeterminism" fix (JM_Project.md §6) — so a tainted item's full graph walk gets redone from scratch on every single call, forever.
3. **The "cycle" is not a bug in any specific mod's recipe — it's ordinary vanilla wood-item structure.** Debug logging (temporary build, see below) showed every cycle-closing recipe ID was vanilla (`minecraft:jungle_chest_boat`, `minecraft:acacia_door`, `minecraft:oak_hanging_sign`, etc.) — real doors/boats/chest-boats/signs needing planks, which is completely normal. The actual trigger is that **some reverse-crafting/"un-craft this back into planks" recipe** (a common, usually-intentional modpack QoL feature — mod not conclusively identified, and not worth chasing further, see below) creates a genuine small 2-item cycle for each reversible wood item: `planks → door` (normal) and `door → planks` (the reverse recipe) together form a cycle. Multiply that across every plank type × every reversible wood item (doors, boats, chest boats, signs, hanging signs), and dozens of small, entirely legitimate cycles sit right in the densest, most commonly-touched part of the whole recipe graph — which is exactly why plain vanilla sticks/logs/stairs trigger it, with or without any specific mod installed.

**Confirmed NOT specific to any one mod:** initially suspected `simplest_paxels` (its `PaxelItem` was one of 20 items caught in the first heap dump's `calculating` set, because paxel recipes reference broad cross-mod tool tags). Removing that mod and reproducing again showed a **different** 19-item cycle — same wood/boat/sign family, an `AxeItem` standing in for the removed `PaxelItem`'s role — proving the mod wasn't the cause, just one of several possible participants. GregTech never triggers this because its recipes don't route through the shared vanilla tool/wood tags at all.

**Net effect:** touching almost any plank-family item (or a modded tool sharing base materials with one) causes the render thread to re-walk a large, cycle-containing subgraph 60 times a second, forever, with no exception ever thrown — indistinguishable from a hang, and invisible to every normal crash-diagnostic channel (crash-reports, latest.log, hs_err_pid) because nothing is actually going wrong from the JVM's perspective, it's just catastrophically slow.

**Fix (not yet implemented, proposed only):**
1. Cache the per-frame threshold lookup in `JourneyModeScreen.renderDepositTab` keyed to the slot's current item; only recompute when the item changes, not every frame.
2. Stop discarding cycle-tainted results forever in `RecipeDepthCalculator` — cache them too (accepting the already-acknowledged theoretical order-dependence in the depth value) rather than paying the full graph-walk cost on every subsequent call. The threshold this feeds is already a soft heuristic (config can override it outright), so this tradeoff is strictly better than a permanent performance cliff.

Together this caps the worst case at "one moderately expensive walk the first time a pathological item is touched," never a hang — and it protects against *any* mod introducing a similar reverse-recipe cycle in the future, not just the one(s) present in this specific repro.

**Diagnostic method note:** a temporary debug-logging build of `RecipeDepthCalculator.java` (Forge 1.20.1 only) was compiled and handed off as a one-off jar to capture the exact cycle chain and closing recipe IDs from the user's own game log. The source edit was reverted immediately after building (`git checkout --`) — `git status` is clean, nothing from that debug pass is committed or left modified in the tree.

## Resolution — 1.8.1

Everything above is fixed. All 9 environments were changed identically (per the §2 non-negotiable), each compiles independently, and all 9 jars were rebuilt from current `HEAD` and re-staged into `release_1.8.1/` after `release_1.8.0/` was deleted outright.

### The deposit-screen freeze — three fixes, not one

The hang needed all three of the compounding factors from §2 to be closed, not just the one that was easiest to reach:

1. **`RecipeDepthCalculator` now memoizes cycle-tainted depths.** This is a deliberate reversal of the 1.8.0 "never cache a tainted result" rule. That rule protected a theoretical property (depth values being purely structural rather than resolution-order-derived) at the cost of a real one (bounded work), and the real one matters more: the value it guards feeds a soft heuristic that config, datapack and dev-API rules override outright. Tainted items are tracked in a `provisionalDepths` set that surfaces in `getDebugInfo` only, so the tradeoff stays visible rather than silent.
2. **The GUI stopped asking per frame.** `JourneyModeScreen.depositThreshold(...)` recomputes only when the deposit slot's item changes or `ConfigHandler.getRulesGeneration()` moves; the progress percentage is derived from that cached threshold rather than a second lookup. `TooltipHandler.thresholdFor(...)` does the same for the tooltip path, which had exactly the same per-frame exposure while the cursor rests on a stack. On 1.12.2 both cache on the full stack (item + metadata + NBT), because its `getThreshold(ItemStack)` overload resolves per hybrid key.
3. **The walk itself is now bounded even without either of the above.** `MAX_RECURSION_DEPTH` (64) stops a long ingredient chain from overflowing the render thread's stack — the `calculating` guard prevented infinite recursion but never deep recursion. `MAX_NODE_VISITS` (250,000) caps total work per top-level query. Two exact early exits shrink the common case dramatically: the per-ingredient loop stops at the first depth-0 option (one broad tag ingredient can expand to hundreds of stacks), and the per-recipe loop stops once `minDepth` hits 1. In the reported repro these alone cut the plank-family walk short before it ever reaches the reverse recipe that closes the cycle.

Layers 2 and 3 are not redundancy for its own sake: layer 1 alone would still leave a single expensive first walk on the render thread, and layers 2–3 alone would leave the recompute-forever behaviour intact for any future caller that doesn't cache.

### The other findings

- **Stale jars** — cause confirmed independently before rebuilding: unzipping the 9 staged `release_1.8.0/` jars and grepping the class constant pools for `SoundEvent` found it in exactly Forge 1.12.2 (`SyncJourneyDataPacket$Handler`), Forge 1.16.5, Forge 1.20.1 and NeoForge 1.21.1 (`ClientSetup`), matching the table in §1 exactly. The same scan over all 9 rebuilt 1.8.1 jars finds zero references anywhere. `release_1.8.0/` was deleted rather than overwritten, and JM_Project.md §14 gained a "Rebuild discipline" subsection so the process failure is recorded next to the release steps it belongs to.
- **Forge 1.19.2 parity gap** — `handleSync` now calls the 6-argument `updateFromSync` and `celebrateNewUnlocks`, with the same `celebrateNewUnlocks` implementation as the other 8. Everything it needed (`getAndClearNewlyUnlocked`, `hasSyncedOnce`, `teamDisplayName` on both the packet and the attachment) already existed on 1.19.2 — only the call site was wrong.
- **Stale comments and the unused import** — cleaned across all 9.
- **Checklist §11** — rewritten to record what actually shipped, that the sound was built and deliberately reverted (with a "do not re-add" note), and that the art-asset half is still deferred.
- **Duplicate notifications** — resolved narrowly, in the direction JM_Project.md §12 already committed to ("batches multiple simultaneous unlocks into one message rather than spamming one per item"). Deposit All no longer emits a chat line per unlocked item; it counts them and reports the total in the summary line it was already printing. The single-deposit chat message is untouched — it's one message for one deliberate action, which was never the complaint.

### Two further defects reported against 1.8.0 during the 1.8.1 work

Both were reported from live play after the audit above and are fixed in the same release.

- **Shift-click withdrew a flat 64 of every item.** `JourneyModeScreen.mouseClicked` sent `hasShiftDown() ? 64 : 1`, and `RequestItemPacket` clamped with a hardcoded `Math.min(count, 64)` — so a request for 64 diamond swords was granted in full, and `Inventory.add()` dutifully spread it across 64 single-item slots. Same for anything else whose limit isn't 64 (potions at 16, and whatever modded items declare). Both ends now use the reconstructed stack's own `getMaxStackSize()`. **The server-side clamp is the one that matters** — the count arrives over the network, so a modified client could ask for 64 of a size-1 item regardless of what the vanilla client sends; fixing only the screen would have left that open. Note this deliberately does *not* re-impose a 64 ceiling: a pack that raises an item's stack limit gets its raised limit, which is the literal meaning of "a full stack". That's a different question from §6's `MAX_BASELINE_STACK_SIZE`, which clamps the *cost* of an item precisely because stack-inflation mods mutate the limit at runtime.
- **Team badge overlapped the screen title.** `titleLabelY` was hardcoded to `-30` and the badge drawn at `y + TAB_Y_OFFSET - 10`, which is also `-30` — the same line, always, on all 8 environments that draw a title (1.12.2 draws none, so it was never affected). Any team name long enough to reach the centred "Journey Mode" ran straight through it. Now `TEAM_BADGE_Y_OFFSET` and `TITLE_Y_OFFSET` are both derived from `TAB_Y_OFFSET`, one line apart, so the three rows can't drift into each other again — the same "one constant, not a second guessed magic number" discipline that fixed the Deposit-All button overlap in 1.8.0.

- **Stats tab per-mod list ran off the bottom of the panel.** `renderStatsTab` drew namespace rows under a hardcoded `rows >= 6` cap with no clearance check of any kind, and the "Latest:" footer sat at a fixed `y + 96` — which overlaps the vanilla `inventoryLabelY` (`imageHeight - 104` = `y + 100`) on its own, before the rows even reach it. On a modpack with six or more namespaces the list ran through the footer and into the "Inventory" label below. Fixed on all 9 by making the list scrollable (mouse wheel; a scrollbar appears only when the list actually overflows) with every position measured against the element below it: `STATS_VISIBLE_ROWS` is now *derived* from the gap between the list top and the footer rather than guessed, the footer moved up to clear the inventory label, and long namespace labels are ellipsized to the width actually available. Forge 1.12.2 had never had the overlap — it already measured its clearance against `PLAYER_INVENTORY_TOP_Y` — but it silently *dropped* rows past the sixth, so it gets the same scrolling treatment.

### Additional issues found by the follow-up audit

Nothing else could hang the game, but three things could degrade or break it under load:

- **Per-frame view rebuilds in the Journey and Stats tabs.** `getFilteredAndSortedItems` was re-derived on every call, and a single frame reaches it twice (grid + tooltip pass) with the mouse handlers on top — so with a search active it rebuilt an `ItemStack` and resolved a display-name `Component` for every unlocked key, several thousand allocations per frame on a large catalog. The Stats tab separately took a full defensive copy of the unlocked set *and* the timestamp map every frame. Both are memoized now: the filter against the live sorted key list (exact, no staleness window), the stats view against a new `syncGeneration` counter bumped by `updateFromSync` — the only path that can change this data client-side. `getUnlockedCount()` replaces the `getUnlockedItems().size()` calls that were copying a whole `HashSet` just to read its size.
- **Unbounded sync payload.** `SyncJourneyDataPacket` sends the entire catalog every time, and vanilla caps a custom-payload packet at 1 MiB on every loader here. Somewhere north of ~12,000 unlocked keys the packet crosses that line, and a client that can't read one is kicked — on every join, which makes the save unplayable rather than merely broken. `syncToClient` now estimates the payload and sheds timestamps, then deposit counts, before building the packet; the unlocked set itself is never truncated and can't reach the ceiling alone. A real delta/chunked sync is the correct long-term fix and is worth scheduling; this guard exists so the failure mode can never be unrecoverable in the meantime.
- **Integer overflow in the progress percentage.** `(count * 100) / threshold` on an `int` goes negative past ~21 million collected. Now `long` math at all 27 sites (`JourneyDataAttachment`/`JourneyData` × 2 overloads and `TeamData` × 1, across all 9), and the deposit screen derives the percentage from its cached threshold rather than making a second lookup.

### Still open (deliberately not done here)

- **`check-parity.ps1`** remains unbuilt (JM_Project.md §2, §14, §16). This incident is the strongest argument yet for it, and the jar-vs-source scan used above — unzip each staged jar, grep the class constant pools for symbols that shouldn't be there — is the first check it should implement, ahead of cross-environment source parity.
- **Delta/chunked data sync**, per the payload note above.
- **`RecipeDepthCalculator.clearCache()` has no callers, on any of the 9.** Pre-existing (it was already dead in 1.8.0), and not a crash or performance risk — but it means the lazily-built recipe index and the depth cache are never invalidated. A `/reload` that changes recipes leaves both stale until the calculator instance is replaced, which only happens when a fresh `JourneyDataAttachment` is created. Two-part fix when it's picked up: make `initializeCalculator` rebuild when the `RecipeManager` it's handed differs from the stored one (covers world switches, ~3 lines), and hook a resource-reload listener per loader family to call `clearCache()` (covers `/reload` proper, and is the part that's actually 4 implementations). Config and datapack threshold rules are unaffected either way — those are consulted fresh on every `calculateThreshold` call, never memoized in the calculator.
- **`isUnlocked(Item)` is O(unlocked-set-size)** — it falls back to a `startsWith` scan for hybrid-key variants. Checked during the audit and deliberately left alone: every actual call site uses the `ItemStack` or `String` overload, both of which are O(1) hash lookups. Worth knowing before wiring the `Item` overload into anything new.
- **No in-game runtime verification was possible in this session** — all 9 environments compile and build clean, and the fixes were verified structurally (bytecode scans of the built jars confirm the new code paths are present in every jar and the sound is absent from every jar), but nothing here was launched and played. The deposit-screen freeze in particular is worth one manual confirmation on the reporter's own modpack before the release goes public.
